# Design: delta compression

Status: format, producers, read path, the unified selection cascade at segment formation (dedup off the WAL write path), and journal-region awareness (identification, the disjoint journal tier, segment segregation, delta-tier exclusion) landed. Proposed, not started: similarity-based source selection. Measurement round 1 (§ Measurement) supports the similarity and journal work.

Date: 2026-07-24 (supersedes the 2026-04 revision)

## The source-selection problem

A delta entry stores an extent as a zstd-compressed diff against a source extent, with the source as the zstd dictionary. The recurring design question is source selection: given a changed extent, which prior extent is the dictionary? Any choice is correct. Dictionary compression produces valid output for any dictionary, and the producer discards a delta that is not smaller than the plain body. A poor source costs compute and forgoes savings, never correctness.

Dedup is the boundary case of the same question: a source identical to the target, encoded as a reference with no bytes (DedupRef). § Unified selection treats it as such.

## Landed system

### Format

Thin `Delta` entries reserve no body space. Each carries one or more delta options (`source_hash` plus offset and length into the segment's delta body section). A source hash must resolve to a DATA entry; there are no delta-of-delta chains, which bounds reads to a single dictionary apply and keeps GC liveness reasoning linear. GC folds `source_hash` into `lba_referenced_hashes`, so a source's DATA entry stays alive while any live LBA reaches it, and carries Delta entries through compaction unchanged. Every live source lives in a snapshot-pinned segment. Full encoding in [formats.md](../formats.md).

### Producers

1. **Import-time path matching.** `elide volume import --extents-from <source>` pairs files by path between the child's ext4 walk and the source snapshot's filemap and computes per-file deltas (`elide-core/src/delta_compute.rs`, in-process in `elide-import`). It needs the source filemap, generated by the operator-invoked `elide volume generate-filemap <source>`; the generation scan demand-fetches evicted ranges and measured ~104s on an 8-deep chain, which is why it is not part of the snapshot path. Without a source filemap the import writes plain DATA entries.
2. **Formation delta tier.** After the exact-hash dedup tier, `execute_promote`'s worker deltas remaining single-block Data entries as each WAL becomes a pending segment. Source selection is same-LBA: the fragment occupying the target's LBA in the latest sealed snapshot is the dictionary, resolved through a snapshot-pinned reader cached across promotes. Best-effort throughout: no sealed snapshot or an unavailable reader skips the tier, and a source body not locally present is skipped, never fetched from S3 to seed a dictionary.

### Filemap

`snapshots/<ulid>.filemap`, line-oriented, one row per contiguous file fragment (`path`, `file_offset`, `blake3`, `byte_count`). Written by import as a side effect of its ext4 walk, or by `generate-filemap`. ext4 volumes only; non-ext4 volumes have no filemap and no path-matched deltas.

### Read path

Delta options are hints. The reader takes the first option whose source is already in local cache; failing that, the option with the earliest source ULID, so hosts make the same choice and their caches converge on shared sources. The delta blob is read from the segment file while pending and from `cache/<id>.delta` after promotion, then decompressed against the source body. A host with no resolvable source fetches the full body where the entry has one; a thin Delta with no resolvable source is a fetch error, symmetric with thin DedupRef.

## Gap

Same-LBA selection misses when file data re-materialises at new LBAs. On ext4 this is not a journaling effect (data blocks are overwritten in place under `data=ordered`); it comes from applications writing a new file and renaming it over the old one, with delayed allocation choosing fresh blocks. Package upgrades and config rewrites follow this pattern.

Extending path matching to this case (pairing paths across the two snapshots' filemaps) needs a filemap at both snapshots, and filemap generation is an operator verb precisely because it is expensive. Same-path lookup also pairs paths, not logical files: content that reappears under a different path (a copied file, a package manager's staged output) has no same-path source. A plain rename is not among the miss cases — `mv` moves no data blocks, so a renamed-in-place file never enters the changed set at all.

## Proposed: similarity-based source selection

Select sources by content resemblance rather than location or path. This needs no filemap, works on any filesystem, and pairs copied or re-pathed files. Measurement round 1 (§ Measurement) recovered ~86% of what path matching achieves on an apt-upgrade workload, without filemaps.

The producer is opportunistic. Every drain tick, as WAL entries form pending segments, each Data entry that misses the exact-hash tier probes a resemblance index over prior data-tier extents and deltas against the best candidate that beats the plain body. The index is built over the live extent index, so the producer needs no snapshot in the volume's history, which is the common case. The same-LBA tier (§ Landed system) stays for a volume that carries a sealed snapshot: it fires first where the target's LBA has a source in the snapshot, and the resemblance probe covers the misses. The WAL write path stays out of scope, since WAL records need plain bytes for crash recovery and segment formation is the earliest point a delta earns anything.

**Sketch.** Per extent, a fixed-size resemblance sketch using the super-feature construction (Broder resemblance; cheap positional computation in the style of Finesse, FAST '19): split the extent into N fixed subchunks, take the maximum Gear rolling-hash value in each, hash feature groups into 8-byte super-features. Extents sharing any super-feature are likely similar; one linear pass over the data. Round 1 measured grouping width as the dominant recall parameter — two-feature groups recovered ~1.6× the bytes of four-feature groups on rebuilt binaries, whose diffuse diffs rarely leave four features jointly intact, and at pair grouping the positional construction matched a position-independent variant within 1%. The working configuration is 16 features in 8 pairs (64 bytes per entry); final parameters are an open question.

**Persistence.** The sketch is stored as a per-entry field in the segment index, a format bump. It then travels with the entry the way the hash does: GC's copy-through preserves it, and a similarity index over any lineage is rebuildable from `.idx` files alone, which `prefetch_indexes` already keeps present without bodies. The alternative, a per-segment sidecar file, avoids the bump but adds an artifact to generate, upload, and keep consistent with the index.

**Producer hook.** At the exact-hash miss in the formation cascade, probe an in-memory map from super-feature to source extents, built over the live data-tier extent index (`inner`). Journal content is a disjoint extent-index tier that never enters `inner` ([gc-journal-segregation.md](gc-journal-segregation.md)), so the index is journal-free by construction, with no window filter on either the build or the query side. A candidate without a locally present body is skipped, never fetched from S3 to seed a dictionary.

**Source policy mirrors dedup.** Dedup admits a source on a single test: the exact hash is already present in the data-tier extent index (`classify_pending_dedup_entries`). No age gate, no coldness gate, no committed-versus-pending distinction; it references whatever owns the hash now, including a source in the same pending batch. The resemblance tier follows the same policy, with a resemblance probe where dedup does the exact lookup and the size check (keep iff smaller than the plain body) where dedup has zero-bytes-always-wins. Sourcing needs no new liveness machinery: a delta's `source_hash` folds into `lba_referenced_hashes` and refcounts through `delta_source_counts` exactly as a dedup target does, so GC keeps an arbitrary source alive as `FLAG_CANONICAL_ONLY` for as long as the delta lives, and the reference releases when the delta's own LBA is overwritten.

**The dedup asymmetry.** A DedupRef's worst case is break-even: one full body serves every reference, and that body persists for any live reference regardless. A Delta's worst case is a bounded net loss. When a source's own LBA is overwritten while only a delta still references it, GC carries the full source body as `FLAG_CANONICAL_ONLY` beside the small delta, to serve an LBA a single full body would have covered. The carry is self-releasing, ending when the delta's LBA is next overwritten, and `CanonicalDelta` keeps the demotion side thin, so a delta that loses its own LBA stays a delta blob rather than re-inflating to its composite. The producer measures this rather than gating against it: a counter for source bodies pinned as `FLAG_CANONICAL_ONLY` that are not independently live, reported per formation and cumulatively beside `DedupMintStats`. That counter decides whether a source gate is worth adding at all.

**Thresholds and granularity.** Only extents above a size threshold are sketched and queried; the delta producer already skips small extents. Resemblance between a small target and a large containing source is low even when the target is a verbatim slice of it, so small-write-into-large-file cases will be missed. Windowed sketches over large sources (one sketch per fixed-size window, all resolving to the same source hash) would close that at the cost of index size; deferred unless the measurement shows the gap matters.

**Failure modes.** A spurious super-feature match produces a delta that fails the size check and is discarded. Entries without sketches (segments written before the bump, sub-threshold extents) contribute no candidates and nothing else changes.

## Journal-region awareness

The jbd2 journal occupies a fixed set of LBA ranges (inode 8, preallocated at mkfs) and is cyclically rewritten with copies of metadata blocks, the shortest-lived data on the device and duplicate by construction. On the round-1 workload the journal was 8.9% of all changed bytes and non-file metadata another 14.1% ([findings.md](../findings.md)). Stored in the shared data tier it deduplicates against durable content, so a journal copy welds into a long-lived segment and keeps that segment from reaping whole long after the journal itself has recycled. The volume stores journal content in a disjoint extent-index tier instead, so it never seeds or satisfies a dedup and each journal segment reaps as a unit.

**Identification.** `ext4_scan::journal_lba_ranges` parses the superblock and walks the journal inode's extent tree through the volume's own read path. The parse is best-effort with a no-opinion rule: not-ext4, an unsupported layout, or an unreadable block yields no opinion, while a successful parse is authoritative — including the empty window for an ext4 filesystem with no internal journal. The answer is persisted in `volume.toml` (the `[journal]` section, absent while never derived) so the index rebuild can apply the window before the filesystem is parseable.

A never-derived volume re-attempts derivation at every promote take, so a filesystem formatted mid-session gains awareness within one drain tick of its first writes (on a blank device each attempt costs one read of LBA 0, the superblock-magic probe failing before deeper parsing). The first successful parse persists the window and the volume begins classifying writes against it. Classification is a persisted per-entry flag: an entry whose LBA falls in a journal range is stamped `JOURNAL` at formation (a `SegmentFlags` bit in the signed index section, no header or magic change), and every rebuild routes by that flag with no window lookup and no replay of history, so the live index, the drift checker, readonly opens, and the coordinator's GC rebuild all agree. An entry written before the window was known carries no flag and stays in the data tier, where it is journal churn that dies within a wrap. A volume whose window was already derived keeps the session-stable rule: a changed window (reformat) persists at open and takes effect at the next open, and an affirmative "not ext4" parse at open clears the section, so a device reformatted away from ext4 reverts to never-derived and the poll resumes. The clear requires written content: an unreadable device or an unwritten superblock keeps the stored window.

**Disjoint tier.** Journal content lives in a separate extent-index map keyed by `(segment ULID, hash)`, never in the data tier's hash-keyed `inner` map (`ExtentIndex::insert_journal_if_absent`, routed by the persisted flag in `register_entry`). The per-segment key means journal content never deduplicates — not against durable content and not across journal segments; identical metadata blocks in two journal segments store two bodies. The data tier stays journal-free, so its admission is plain lowest-ULID-wins with no journal special case. A read resolves a journal-window LBA through the writing segment's claimant (`lookup_journal(claimant, hash)`) rather than the shared hash lookup, so the same content at a durable LBA and a journal LBA serves from its own tier.

**Segment segregation.** A promote whose epoch touched journal LBAs writes a segment pair: the durable share under the first ULID, the journal-window share under a second, higher ULID. jbd2 is a circular log, so a journal segment's claims die together at the next wrap and the whole file is reaped rather than folding live neighbours out of a mixed segment. GC pool-isolates journal segments, packing them into nothing and reaping them whole once a newer segment claims their LBAs ([gc-journal-segregation.md](gc-journal-segregation.md)); a consolidation pass merges a tick's small journal segments into one before upload. The higher journal ULID keeps durable content below its journal in ULID order, which upload preserves. An epoch with no journal writes forms a single segment as before.

**Delta exclusion.** The formation delta tier never sees journal entries (the journal partition skips the tier structurally), and journal-window runs are dropped from the `SnapshotSourceMap`, so journal content never seeds a dictionary from either side.

**Similarity exclusion is structural.** The resemblance index builds over the data tier (`inner`), which journal content never enters, so journal extents are absent from both its build and its query with no window check. This is a property of the disjoint-tier layout rather than a filter the producer applies; the snapshot same-LBA map still drops journal-window runs explicitly (`SnapshotSourceMap::build`) because it reconstructs its own LBA map from snapshot layers.

## Unified selection at segment formation

The format treats thin DedupRef and thin Delta as siblings: `stored_length = 0`, resolution through `extent_index.lookup`, the same `lba_referenced_hashes` liveness rule, the same GC copy-through. The producer side matches: segment formation classifies every entry once.

**The cascade.**

1. Exact-hash hit in the extent index → DedupRef. Verification is hash equality; zero bytes always wins, no size check.
2. A delta source found for the extent → compute the zstd-dictionary delta, keep iff smaller than the stored body. Two source-finders feed this step: same-LBA in a sealed snapshot where one exists (landed), and the opportunistic resemblance probe over the live data tier (proposed). Same-LBA runs first when a snapshot is present; the resemblance probe covers the rest and needs no snapshot.
3. Otherwise → Data (or Inline/Zero per the existing rules).

The reclaim workers' existing exact-first ordering ("DedupRef strictly beats any Delta") is the cascade's priority rule.

**One policy surface.** Candidate filters — journal-range exclusion (both directions), the source-age gate, the source-body-locally-present rule, snapshot scoping — apply once, at the cascade, rather than separately in a write-path check, a tick pass, and reclaim conversion.

**Dedup is off the WAL write path.** Writes always append full body records; the write path keeps hashing and compression but takes no dedup decision. The no-op skip (same LBA, same hash, no append) stays: it creates no cross-reference and covers the common unchanged-page rewrite. Consequences:

- The WAL is self-contained at crash recovery: no record's readability depends on segment-store canonical presence.
- Reading back just-written data is local until promote. A thin WAL REF could resolve to an evicted canonical and demand-fetch from S3.
- The hot path needs no filesystem awareness; the journal range set is consulted only at formation.
- Duplicate-content writes carry full bodies in the WAL until the next promote thins them. Write-path dedup hits are a small fraction of real ublk traffic, and the cost is bounded by the promote threshold.
- The WAL REF record kind is parse-only legacy format.

Pending segments carry DedupRef entries minted at formation, on the actor at take time; the delta tier runs in the promote worker, off-lock.

**Where unification stops.** DedupRef and Delta remain distinct entry kinds with distinct read paths. The boundary case has load-bearing properties the general case lacks: a DedupRef read fetches nothing beyond the body its own hash names; verification is free and has no false-positive concept; and its sources are perfectly interchangeable (any canonical with the hash serves), where a delta is pinned to specific source bytes.

## Measurement

The offline experiment runs via `elide delta-sim <before.img> <after.img>` over two states of one live-written ext4 filesystem (`scripts/delta-sim-workload` generates a pair via an in-place apt upgrade). It replays same-LBA selection over the changed blocks, runs the sketch match over the misses with real zstd-dictionary ratios, buckets journal-range and non-file metadata bytes separately, and bounds what path matching would achieve with a same-path oracle.

Round 1 (2026-07-20, full numbers in [findings.md](../findings.md)): same-LBA selection found sources for 5.7% of changed file-data bytes; similarity recovered 30% of the miss bytes, which is ~86% of the same-path oracle's recovery plus 22 MiB the oracle cannot reach; every surviving match beat LZ4 (zero false positives past the size check); journal plus metadata was 23% of changed bytes. The largest unrecovered bucket was apt's downloaded archives and lists — new high-entropy content with no source under any strategy. One workload on a fresh filesystem; a second round on an aged filesystem or a different churn profile would strengthen the numbers.

## Open questions

- Final sketch parameters. Round 1 fixed the grouping question (pairs, not quadruples) but not the feature count or the per-entry size/recall tradeoff (8 pairs cost 64 bytes per index entry against the 24 bytes a 12/4/3 split would). The Broder-versus-Finesse choice rides here: round 1 measured them within 1% at pair grouping, and Finesse is the cheaper positional pass.
- Windowed sketches for large sources.
- Cross-lineage sources. Whether the resemblance index admits ancestor-volume extents as candidates, and whether the source refcount holds across the lineage boundary as it does within one volume's map.
- Whether the entanglement counter ever warrants a source gate, decided by rig measurement rather than up front.
- Write-path dedup incidence: how much WAL growth promote-time DedupRef minting costs on real traffic, and the retirement path for the WAL REF record kind.
- Filemap hardlinks produce duplicate rows with different paths and the same hash; harmless, worth deduplicating for compactness.
