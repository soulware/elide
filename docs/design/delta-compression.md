# Design: delta compression

Status: format, producers, read path, the unified selection cascade at segment formation (dedup off the WAL write path), journal-region awareness (identification, the disjoint journal tier, segment segregation, delta-tier exclusion), per-entry resemblance sketches (computed and persisted at formation), the two-bar keep rule, the candidate map (`elide_core::sketch_index`), and source liveness landed. Proposed, not started: the growth questions in § Open questions. Measurements in § Measurement support the similarity, journal, and geometry work.

Date: 2026-07-25 (supersedes the 2026-04 revision)

## The source-selection problem

A delta entry stores an extent as a zstd-compressed diff against a source extent, with the source as the zstd dictionary. The recurring design question is source selection: given a changed extent, which prior extent is the dictionary? Any choice is correct. Dictionary compression produces valid output for any dictionary, and the producer discards a delta that is not smaller than the plain body. A poor source costs compute and forgoes savings, never correctness.

Dedup is the boundary case of the same question: a source identical to the target, encoded as a reference with no bytes (DedupRef). § Unified selection treats it as such.

## Landed system

### Format

Thin `Delta` entries reserve no body space. Each carries one or more delta options (`source_hash` plus offset and length into the segment's delta body section). A source hash must resolve to a DATA entry; there are no delta-of-delta chains, which bounds reads to a single dictionary apply and keeps GC liveness reasoning linear.

GC folds `source_hash` into `lba_referenced_hashes`, so a source's DATA entry stays alive while any live LBA reaches it, and carries Delta entries through compaction unchanged. Full encoding in [formats.md](../formats.md).

One option names exactly one source. Combining several extents into one dictionary was measured (round 2, § Measurement) and rescued no target that a single source missed, leaving aggregate delta size unchanged, so the residual recall gap is content with no source rather than content spread across two. It would also have cost a format change and multiplied the entanglement: a delta pinning N bodies stays readable only while all N resolve, so the `FLAG_CANONICAL_ONLY` carry releases on a conjunction and a read needs N body reads.

### Producers

1. **Import-time path matching.** `elide volume import --extents-from <source>` pairs files by path between the child's ext4 walk and the source snapshot's filemap and computes per-file deltas (`elide-core/src/delta_compute.rs`, in-process in `elide-import`). It needs the source filemap, generated by the operator-invoked `elide volume generate-filemap <source>`; the generation scan demand-fetches evicted ranges and measured ~104s on an 8-deep chain, which is why it is not part of the snapshot path. Without a source filemap the import writes plain DATA entries.
2. **Formation delta tiers.** After the exact-hash dedup tier, `execute_promote`'s worker converts remaining Data entries as each WAL becomes a pending segment, over two source-finders in cascade order. Same-LBA takes single-block entries whose LBA the latest sealed snapshot holds a different extent for, resolved through a snapshot map cached across promotes. Resemblance then takes what it left alone, probing the candidate map (§ Producer hook) for a source by content, which needs no snapshot. Best-effort throughout: an unavailable source map skips its tier, and a source body not locally present is skipped, never fetched from S3 to seed a dictionary.

### Filemap

`snapshots/<ulid>.filemap`, line-oriented, one row per contiguous file fragment (`path`, `file_offset`, `blake3`, `byte_count`). Written by import as a side effect of its ext4 walk, or by `generate-filemap`. ext4 volumes only; non-ext4 volumes have no filemap and no path-matched deltas.

### Read path

Delta options are hints. The reader takes the first option whose source is already in local cache; failing that, the option with the earliest source ULID, so hosts make the same choice and their caches converge on shared sources. The delta blob is read from the segment file while pending and from `cache/<id>.delta` after promotion, then decompressed against the source body. A host with no resolvable source fetches the full body where the entry has one; a thin Delta with no resolvable source is a fetch error, symmetric with thin DedupRef.

## Gap

Same-LBA selection misses when file data re-materialises at new LBAs. On ext4 this is not a journaling effect (data blocks are overwritten in place under `data=ordered`); it comes from applications writing a new file and renaming it over the old one, with delayed allocation choosing fresh blocks. Package upgrades and config rewrites follow this pattern.

Extending path matching to this case (pairing paths across the two snapshots' filemaps) needs a filemap at both snapshots, and filemap generation is an operator verb precisely because it is expensive. Same-path lookup also pairs paths, not logical files: content that reappears under a different path (a copied file, a package manager's staged output) has no same-path source. A plain rename is not among the miss cases — `mv` moves no data blocks, so a renamed-in-place file never enters the changed set at all.

## Similarity-based source selection

Sources are selected by content resemblance rather than location or path. This needs no filemap, works on any filesystem, and pairs copied or re-pathed files. Measurement round 1 (§ Measurement) recovered ~86% of what path matching achieves on an apt-upgrade workload, without filemaps.

The producer is opportunistic. Every drain tick, as WAL entries form pending segments, each Data entry that misses the exact-hash tier probes the candidate map and deltas against the first candidate that clears the keep rule. The map spans the lineage's persisted sketches, so the producer needs no snapshot in the volume's history, which is the common case. The same-LBA tier stays for a volume that carries a sealed snapshot: it fires first where the target's LBA has a source in the snapshot, and the resemblance probe covers the misses. The WAL write path stays out of scope, since WAL records need plain bytes for crash recovery and segment formation is the earliest point a delta earns anything.

**Sketch.** Per extent, a fixed-size resemblance sketch. Sample window positions by content, where the low bits of a Gear rolling hash are all-ones (about 1 in 32 positions), and take the maximum of one independent permutation per feature over the sampled window hashes. Each maximum is a minhash, so the probability that two extents agree on a given feature is their resemblance over sampled windows, and extents sharing any value are likely similar, over one linear pass of the raw bytes. This position-independent Broder construction survives insertions and deletions, where a positional Finesse pass over fixed subchunks shifts every subchunk after an edit. Computed at segment formation over the entry's decompressed body (`elide_core::sketch`). A Data entry that carries a delta, is journal-tier, or samples too few windows to be meaningful is left unsketched. The persisted form is eight ungrouped 4-byte features, 32 bytes per entry, for extents of at least 32 KiB (`sketch::MIN_SKETCH_BYTES`).

**Why ungrouped, and why four bytes.** Grouping features into super-features, which is what the super-feature literature adds to plain minhash, requires all features in a group to agree and so drops the per-value match probability from `r` to `r^k`. Round 2 (§ Measurement) measured that as costing far more recall than it buys. Holding the stored value count at eight, so that sketch bytes and map size are identical and grouping is the only variable, recall against sources a same-path oracle proves exist runs 58% at four-feature groups, 81% at pairs, and 94% ungrouped. Grouping is a precision filter, and it is precision the producer already has for free: the size check verifies every candidate exactly, and a rejected one costs a single discarded delta attempt. Ungrouped features also make the count of features two extents share a direct estimate of their resemblance, which is what the candidate ranking sorts on, where grouping destroys that signal by construction.

The width of a stored value is a false-positive knob and never a recall one, since whether two extents agree on a feature is decided by the content and the permutation, not by how much of the resulting value is kept. Four-byte and eight-byte values measured bit-identical on every recovery number, so the narrower field is free. Two-byte values inflate apparent recovery through collisions while saving no additional bytes, a spurious match costing one discarded delta attempt. Four bytes also makes a posting exactly eight bytes in the candidate map.

**Persistence.** The sketch is a per-entry field in the segment index. It travels with the entry the way the hash does: GC's copy-through preserves it, and a similarity index over any lineage is rebuildable from `.idx` files alone, which `prefetch_indexes` already keeps present without bodies. A body is the one thing a host may not have, so a derivable-from-bytes field still has to be stored. The alternative, a per-segment sidecar file, would have avoided the format bump but added an artifact to generate, upload, and keep consistent with the index.

The size threshold is what keeps this affordable. A base index entry is 64 bytes, so a sketched entry more than doubles its own index footprint, on the one artefact that is resident on every host and parsed at every open. Sketching only extents of at least 32 KiB keeps that off the small entries a probe would never pick as sources anyway.

**Producer hook.** At the exact-hash miss in the formation cascade, `delta_pendings_by_resemblance` probes an in-memory multimap from feature value to source extent, over the entries the same-LBA tier left alone. Journal content is a disjoint extent-index tier ([gc-journal-segregation.md](gc-journal-segregation.md)) and journal entries carry a persisted flag, so the index is journal-free by construction with no window filter on either the build or the query side. A candidate without a locally present body is skipped, never fetched from S3 to seed a dictionary.

The map is a cache, not index state. Every candidate resolves through the live extent index before use, so a stale posting costs one failed lookup and a missing one costs a missed delta. It therefore stays out of `ExtentIndex`, which would give it the rebuild-equality invariant, the drift checker, and a clone into every reader snapshot, all to protect a structure whose failure mode is a missed optimisation. The volume holds it beside the extent index and hands the worker an `Arc` per promote.

Staleness covers the one hazard a live-index probe would otherwise have. A candidate can never come from the batch being formed, since the map is extended when a promote's result is applied, so no conversion can leave another conversion's source pointing at a `Delta`. An entry that later becomes a delta loses its sketch and its hash leaves the data tier, so a posting naming it stops resolving.

Shape is a flat open-addressed multimap of `(feature, source id)` slots, eight bytes each with no per-key allocation, over an arena of `(hash, raw length)` per source. Duplicate keys occupy adjacent slots, so a probe is one slot index plus a linear run scan, and resize is a plain rehash. The arena's length field lets a probe reject a source far larger than the target before paying for the body read.

A probe is eight lookups, one per feature, whose postings are tallied per source and ranked by shared-feature count (`elide_core::sketch_index`). Ungrouped features raise candidates surfaced per probe from 13 to 72, which the ranking and the cap absorb, and a per-feature posting cap of 32 bounds any probe to 256 candidates however large the index grows. That cap keeps a feature shared by hundreds of extents, which says nothing about which of them resembles a target, from dominating the map and every probe touching it. Retention on the cap is earliest-wins, which keeps the oldest sources carrying a feature: the build walk is ULID-ascending, so those are imported base-image extents rather than churn, and the map stays a deterministic function of the lineage.

**Trying candidates.** One dictionary per target. Walk the ranking for a source whose body is locally readable, compress against it, and stop either way: a delta that clears the keep rule converts the entry, and one that fails ends the target rather than moving down the list. Round 2 measured the bytes rescued by a lower-ranked candidate after the top-ranked one lost at 0 MiB in 0 runs, so a tried-and-lost result is a fact about the target rather than about that source. Recovery was likewise identical at caps of 1 through 32, with delta size varying 0.7%.

What the cap bounds is therefore depth, not width. A candidate can be unusable for reasons the map cannot see, since a source body that is not locally present, has its presence bit clear, or will not decompress is declined and never fetched to seed a dictionary; the next-ranked source covers that, and skipping it costs nothing because nothing was tried.

A floor on shared features, requiring several rather than one before a source is worth trying, is the same lever as grouping applied at query time and loses on the same grounds. Round 2 measured recall falling from 94.1% to 87.5% at a floor of two and to 60.2% at four, while candidates surfaced barely moved, since the posting runs are walked to count shared features before any floor can apply. With only one dictionary compressed against per target, there is nothing left for a floor to save.

Nothing available ranks sources by how costly they are to become entangled with, which is a further reason not to optimise the choice on size alone.

Feeding it costs nothing extra at open. Signature verification dominates the build, and the rebuild walk already verifies every `.idx` in the lineage, so `rebuild_with_sketches` harvests during that walk rather than paying for a second one. Each promote's own sketched entries are added when its result is applied, and the map rebuilds on process start. `elide sketch-index <fork-dir>` builds it offline and reports its shape.

**Source policy mirrors dedup.** Dedup admits a source on a single test: the exact hash is already present in the data-tier extent index (`classify_pending_dedup_entries`). No age gate, no coldness gate, no committed-versus-pending distinction; it references whatever owns the hash now, including a source in the same pending batch. The resemblance tier follows the same policy, with a resemblance probe where dedup does the exact lookup and the two-bar keep rule where dedup has zero-bytes-always-wins. A delta's `source_hash` is recorded per segment in the extent index's delta-source records at registration, and every deletion decision unions those named sources with the claim set (`ExtentIndex::named_delta_sources`), so GC keeps an arbitrary source alive as `FLAG_CANONICAL_ONLY` for as long as any segment entry names it; the pin releases when the last naming encoding leaves its segment.

**Source liveness.** A delta is the only reference a promote commits that can name an extent no LBA claims. A DedupRef or a carried entry names content some LBA still claims, which any concurrent rewrite has to carry forward, so it survives a GC pass for free. A delta's source is kept present by three things. Selection admits only sources the volume's referenced view reports — claims plus the named delta sources (`LbaMap::referenced_hashes`). A finished GC plan's apply is held until no promote is in flight (`actor::apply_or_defer_gc_plan`), so a plan computed before the delta's reference exists cannot land after it. And a plan that would drop a hash the lbamap now references is refused (`volume::apply_plan_apply_result`). Safety rests on the last two, measured by ablation in `specs/DeltaSourceLiveness.tla`. The selection filter is a cost measure, keeping a promote from pinning a source GC was about to free, and from provoking the refusal that discards a whole pass of rewrites.

Cross-lineage sources need nothing beyond that. A fork pins a parent snapshot, since `fork_volume` refuses a source that has none, and a fork's GC skips every segment at or below `latest_snapshot`, so no ancestor extent a child can name is a GC candidate in the volume that owns it. The floor only rises, being the max over User manifests, and only stop-snapshots are ever deleted. Reclaim already treats that pin as its stickiest signal that a source body will persist.

**The dedup asymmetry.** A DedupRef's worst case is break-even: one full body serves every reference, and that body persists for any live reference regardless. A Delta's worst case is a bounded net loss. When a source's own LBA is overwritten while only a delta still references it, GC carries the full source body as `FLAG_CANONICAL_ONLY` beside the small delta, to serve an LBA a single full body would have covered. The carry is self-releasing, ending when the encoding naming the source is itself dropped — a delta whose LBA is overwritten falls out at the next rewrite of its segment, and the pin lapses with its record — and `CanonicalDelta` keeps the demotion side thin, so a delta that loses its own LBA stays a delta blob rather than re-inflating to its composite. The producer measures this rather than gating against it: a counter for source bodies pinned as `FLAG_CANONICAL_ONLY` that are not independently live, reported per formation and cumulatively beside `DedupMintStats`. That counter decides whether a source gate is worth adding at all.

**Thresholds and granularity.** The 32 KiB threshold gates three things from one constant: which entries the producer sketches, which enter the candidate map, and which the resemblance tier probes as targets. The target side needs its own filter because the same-LBA tier's `lba_length == 1` restriction comes from its per-LBA source map and does not apply here.

Resemblance between a small target and a large containing source is low even when the target is a verbatim slice of it, so small-write-into-large-file cases are missed. Windowed sketches over large sources (one sketch per fixed-size window, all resolving to the same source hash) would close that at the cost of index size; deferred unless measurement shows the gap matters.

**Failure modes.** A spurious feature match produces a delta that fails the keep rule and is discarded. Entries without sketches (sub-threshold extents, segments written before the field existed) contribute no candidates and nothing else changes.

## Journal-region awareness

The jbd2 journal occupies a fixed set of LBA ranges (inode 8, preallocated at mkfs) and is cyclically rewritten with copies of metadata blocks, the shortest-lived data on the device and duplicate by construction. On the round-1 workload the journal was 8.9% of all changed bytes and non-file metadata another 14.1% ([findings.md](../findings.md)). Stored in the shared data tier it deduplicates against durable content, so a journal copy welds into a long-lived segment and keeps that segment from reaping whole long after the journal itself has recycled. The volume stores journal content in a disjoint extent-index tier instead, so it never seeds or satisfies a dedup and each journal segment reaps as a unit.

**Identification.** `ext4_scan::journal_lba_ranges` parses the superblock and walks the journal inode's extent tree through the volume's own read path. The parse is best-effort with a no-opinion rule: not-ext4, an unsupported layout, or an unreadable block yields no opinion, while a successful parse is authoritative — including the empty window for an ext4 filesystem with no internal journal. The answer is persisted in `volume.toml` (the `[journal]` section, absent while never derived) so the index rebuild can apply the window before the filesystem is parseable.

A never-derived volume re-attempts derivation at every promote take, so a filesystem formatted mid-session gains awareness within one drain tick of its first writes (on a blank device each attempt costs one read of LBA 0, the superblock-magic probe failing before deeper parsing). The first successful parse persists the window and the volume begins classifying writes against it. Classification is a persisted per-entry flag: an entry whose LBA falls in a journal range is stamped `JOURNAL` at formation (a `SegmentFlags` bit in the signed index section, no header or magic change), and every rebuild routes by that flag with no window lookup and no replay of history, so the live index, the drift checker, readonly opens, and the coordinator's GC rebuild all agree. An entry written before the window was known carries no flag and stays in the data tier, where it is journal churn that dies within a wrap. A volume whose window was already derived keeps the session-stable rule: a changed window (reformat) persists at open and takes effect at the next open, and an affirmative "not ext4" parse at open clears the section, so a device reformatted away from ext4 reverts to never-derived and the poll resumes. The clear requires written content: an unreadable device or an unwritten superblock keeps the stored window.

**Disjoint tier.** Journal content lives in a separate extent-index map keyed by `(segment ULID, hash)`, never in the data tier's hash-keyed `inner` map (`ExtentIndex::insert_journal_if_absent`, routed by the persisted flag in `register_entry`). The per-segment key means journal content never deduplicates — not against durable content and not across journal segments; identical metadata blocks in two journal segments store two bodies. The data tier stays journal-free, so its admission is plain lowest-ULID-wins with no journal special case. A read resolves a journal-window LBA through the writing segment's claimant (`lookup_journal(claimant, hash)`) rather than the shared hash lookup, so the same content at a durable LBA and a journal LBA serves from its own tier.

**Segment segregation.** A promote whose epoch touched journal LBAs writes a segment pair: the durable share under the first ULID, the journal-window share under a second, higher ULID. jbd2 is a circular log, so a journal segment's claims die together at the next wrap and the whole file is reaped rather than folding live neighbours out of a mixed segment. GC pool-isolates journal segments, packing them into nothing and reaping them whole once a newer segment claims their LBAs ([gc-journal-segregation.md](gc-journal-segregation.md)); a consolidation pass merges a tick's small journal segments into one before upload. The higher journal ULID keeps durable content below its journal in ULID order, which upload preserves. An epoch with no journal writes forms a single segment as before.

**Delta exclusion.** The formation delta tier never sees journal entries (the journal partition skips the tier structurally), and journal-window runs are dropped from the `SnapshotSourceMap`, so journal content never seeds a dictionary from either side.

**Similarity exclusion is structural.** The resemblance index builds over the data tier (`inner`), which journal content never enters, so journal extents are absent from both its build and its query with no window check. This is a property of the disjoint-tier layout rather than a filter the producer applies; the snapshot same-LBA map still drops journal-window runs explicitly (`SnapshotSourceMap::build`) because it reconstructs its own LBA map from snapshot layers.

## Unified selection at segment formation

The format treats thin DedupRef and thin Delta as siblings: `stored_length = 0`, resolution through `extent_index.lookup`, the same `lba_referenced_hashes` liveness rule, the same GC copy-through. The producer side matches: segment formation classifies every entry once.

**The cascade.**

1. Exact-hash hit in the extent index → DedupRef. Verification is hash equality; zero bytes always wins, no size check.
2. A delta source found for the extent → compute the zstd-dictionary delta, keep iff it clears both bars (§ The two-bar keep rule). Two source-finders feed this step: same-LBA in a sealed snapshot where one exists (landed), and the opportunistic resemblance probe over the live data tier (proposed). Same-LBA runs first when a snapshot is present; the resemblance probe covers the rest and needs no snapshot.
3. Otherwise → Data (or Inline/Zero per the existing rules).

### The two-bar keep rule

A delta is kept only if it is smaller than both the stored body and what plain zstd achieves on the same plaintext (`delta_compute::delta_is_worth_storing`, used by both producers).

The first bar keeps the stored bytes from growing. The second is what makes the tier mean what it is named for. Bodies are stored LZ4, and zstd is the stronger codec on compressible content, so beating the stored body alone can be true with no contribution from the dictionary at all. Round 2 measured that as 27% of everything the tier recovered.

Those conversions are the worst trade in the system. The entry acquires a source dependency, so a read resolves a source hash, reads a second body that contributes nothing to its content, and applies a dictionary decompress, where one body read would have done. GC inherits the dependency through `lba_referenced_hashes` and carries the source body as `FLAG_CANONICAL_ONLY` for as long as the delta lives. The pairing is arbitrary, since the dictionary earned none of it. And the saving was reachable with no dependency at all by encoding that extent with zstd instead of LZ4, which makes it a codec saving rather than a delta one.

Plain zstd is never stored. Bodies stay LZ4 because decompression speed is on the read path, and the control exists only as a number to compare against. Declining a delta leaves the entry as the Data entry it already was, so there is no fallback path and nothing to unwind. The control costs one zstd compress per entry that clears the first bar, at formation on the promote worker.

A consequence is that deltas against `Inline` sources no longer fire. An Inline entry holds under 256 stored bytes, so its content is compressible enough that plain zstd already captures whatever its dictionary could offer.

Whether the second bar should carry a margin, so a delta must beat the control by some amount rather than by a byte, is left to the entanglement counter (§ The dedup asymmetry) rather than picked up front.

The reclaim workers' existing exact-first ordering ("DedupRef strictly beats any Delta") is the cascade's priority rule.

**One policy surface.** Candidate filters — journal-range exclusion (both directions), the source-age gate, the source-body-locally-present rule, snapshot scoping — apply once, at the cascade, rather than separately in a write-path check, a tick pass, and reclaim conversion.

**Dedup is off the WAL write path.** Writes always append full body records; the write path keeps hashing and compression but takes no dedup decision. The no-op skip (same LBA, same hash, no append) stays: it creates no cross-reference and covers the common unchanged-page rewrite. Consequences:

- The WAL is self-contained at crash recovery: no record's readability depends on segment-store canonical presence.
- Reading back just-written data is local until promote. A thin WAL REF could resolve to an evicted canonical and demand-fetch from S3.
- The hot path needs no filesystem awareness; the journal range set is consulted only at formation.
- Duplicate-content writes carry full bodies in the WAL until the next promote thins them. Write-path dedup hits are a small fraction of real ublk traffic, and the cost is bounded by the promote threshold.
- The WAL REF record kind is parse-only legacy format.

Pending segments carry DedupRef entries minted at formation, on the actor at take time; the delta tier runs in the promote worker, off-lock.

**Where unification stops.** DedupRef and Delta remain distinct entry kinds with distinct read paths. The boundary case has load-bearing properties the general case lacks: a DedupRef read fetches nothing beyond the body its own hash names; verification is free and has no false-positive concept; and its sources are perfectly interchangeable (any canonical with the hash serves), where a delta is pinned to specific source bytes.

## Measurement

The offline experiment runs via `elide delta-sim <before.img> <after.img>` over two states of one live-written ext4 filesystem (`scripts/delta-sim-workload` generates a pair via an in-place apt upgrade). It replays same-LBA selection over the changed blocks, runs the sketch match over the misses with real zstd-dictionary ratios under the production keep rule, buckets journal-range and non-file metadata bytes separately, and bounds what path matching would achieve with a same-path oracle. The sketch geometry is parameterised (`--features`, `--group`, `--sf-bytes`), the dictionaries tried per target are capped (`--max-candidates`), `--dict-sources` builds one dictionary from several ranked candidates alongside the single-source result, and `--train-dict` trains one shared dictionary over the before-image and measures it against the baseline each bucket already has, so a sweep is a series of runs over one image pair.

Round 1 (2026-07-20, full numbers in [findings.md](../findings.md)): same-LBA selection found sources for 5.7% of changed file-data bytes; similarity recovered 30% of the miss bytes, which is ~86% of the same-path oracle's recovery plus 22 MiB the oracle cannot reach; journal plus metadata was 23% of changed bytes. The largest unrecovered bucket was apt's downloaded archives and lists, new high-entropy content with no source under any strategy.

Round 2 (2026-07-25, full numbers in [findings.md](../findings.md)) swept the sketch geometry and separated the dictionary's contribution from the codec's. Grouping dominates recall in the direction round 1 only sampled one step of, and ungrouped features at half the persisted size recover 20% more dictionary-attributable bytes than the shipping geometry. Feature count is the weaker knob at pair grouping, worth 2.3 MiB where round 1's per-pair fit predicted several times that, because the pairs a sketch misses are the low-resemblance tail the aggregate fit understates; ungrouped its slope is steeper, with a knee around eight features. Width is inert. The candidate cap is inert once candidates are ranked by shared-feature count.

Round 2 also found the measurement flaw that the two-bar keep rule fixes. Round 1's criterion was zstd-with-dictionary against LZ4, which conflates the codec with the dictionary, so its recovery figures include bytes no dictionary earned.

## Open questions

- Windowed sketches for large sources.
- Candidate volume at production index sizes. Ungrouped features surface 72 candidates per probe over the 1,911-source measurement index, and volume scales with index size, so the per-feature posting cap is what bounds it. Its effect on recall at 10⁴ to 10⁵ sources is unmeasured.
- Whether the entanglement counter ever warrants a source gate, or a margin on the second keep bar, decided by rig measurement rather than up front.
- Trained shared dictionaries, on a workload with a large sub-threshold population. A dictionary trained over a corpus of extents inverts the properties a source-as-dictionary has: it pins nothing live, so there is no `FLAG_CANONICAL_ONLY` carry and no entanglement to count; it costs its own storage once, amortised across every entry referencing it; and it needs no per-entry metadata, so it reaches the extents too small to afford a sketch. Round 2 measured it earning 0.5 to 0.8 MiB against similarity's 40.4 MiB, nothing at all on already-compressed content with no source, and 2.6× worse than a near-copy where one exists. Its value scales with the sub-threshold population, which that workload barely has, so what stays open is whether a small-file churn profile changes the answer. Distinct from combining source extents into one dictionary, which round 2 closed outright.

  Storage would need little new machinery. A trained dictionary is a body with no LBA claim, which is what `FLAG_CANONICAL_ONLY` already means, so writing it as a `CanonicalData` entry gives it a content hash to be named by, the segment signature over its index entry, upload and demand-fetch as an ordinary body, and liveness through `delta_source_counts` for as long as a delta references it. The sharp edge is that every canonical-only entry today arrives by demotion, its LBA having died, where this one would be born that way and never have had one; GC's handling of an entry in that state is what would need checking first.
- Whether the body codec should be zstd. Round 2 measured plain zstd beating LZ4 on 62 MiB of ordinary extents, which the two-bar rule now declines to collect through deltas. Collecting it directly means a per-entry codec field and read-path support everywhere, against LZ4's decompression speed on the read path.
- Write-path dedup incidence: how much WAL growth promote-time DedupRef minting costs on real traffic, and the retirement path for the WAL REF record kind.
- Filemap hardlinks produce duplicate rows with different paths and the same hash; harmless, worth deduplicating for compactness.
